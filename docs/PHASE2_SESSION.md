# Phase 2: session ownership and legacy migration

The session owns the transferred byte transport, connection lifetime, one continuous reader, a bounded transaction queue and recovery. Profiles remain pure. Commands and verification queries run in one queue item; cancellation and admission deadlines include queue wait. A rejected or cancelled queued command is not written. After I/O begins, failure cannot establish that a mutation did nothing: results preserve write evidence and uncertainty. Ambiguous replies, transport loss and timeout fault the connection before another queued transaction may run. Explicit reconnect is required; operations are never automatically replayed.

Supported legacy ASCII `IRadio.ConnectAsync(ISerialPort)` calls automatically create that owner. The caller transfers exclusive use and disposal of the port and must stop reading, writing, closing or disposing it independently. Disconnect closes but retains the transport for an explicit reconnect using the same object. Disposing the radio disposes its session and transport permanently. Failed facade startup disposes the session; supply a fresh port for another attempt. Never reuse a disposed adapter or substitute a different object with the same port name.

`BaseRadio.ExecuteCommandAsync` exposes typed results for the compatibility command path. Legacy `SendCommandAsync` returns null on failure and an empty string on successful write-only completion. Completion means the declared policy finished, not hardware acceptance. Frequency/mode profile read-back and manufacturer-specific response validation are Phase 3 work. The ASCII compatibility matcher only establishes a complete frame with the expected opcode; it does not certify a model or setting. Failed status reads report failure rather than fabricate zero/USB observations. Cached legacy properties alone are not observation evidence.

ResilientSerialPort and ResilientRadio are passive compatibility wrappers. Retry/recovery/health settings remain source-compatible but are inert; neither starts a timer or repeats a mutation. RealSerialPort uses native byte writes. String-only third-party ports accept ASCII bytes only and must respect finite read/write timeouts and close-to-unblock for bounded shutdown. No adapter subscribes to DataReceived to consume bytes.

The console transfers an unopened port and uses the radio command path once. It no longer reads serial event data or sends raw writes on failure. Legacy TCP response presentation is still unframed and arrives through the existing broadcast mechanism; correlation and notification delivery are Phase 4 work. This phase makes no claim that the current TCP wire path is reliable.

Auto-detection and live model switching are explicitly unavailable: neither may create another reader or reuse a disposed transferred port. Configure a model at startup. Models without a supported ASCII mapping, including the CI-V placeholders, reject connection before sending commands. Experimental ASCII facades do not establish manufacturer support. DummyRadio requires a fake port (or its explicit dummy default); wrapped physical ports are rejected instead of substituted. The legacy dummy engine always echoes; its facade consumes that known echo in the same transaction, including write-only calls, and preserves their empty response presentation. Direct session consumers must use the dummy engine's reply-required policy. Its existing command engine is transported through the session and is not the independent FT-991A emulator planned for Phase 3.

CAT has no transaction identifiers. A connection generation and opcode match cannot prove a device abandoned an arbitrarily delayed prior reply. Fault/close prevents continued command execution on the ambiguous stream; explicit reopening and an ID exchange are not universal synchronization proof. The FT-991A profile must establish its startup/automatic-information/quiet-drain policy in Phase 3, with deterministic tests of its limits. Hardware behavior remains unverified.
