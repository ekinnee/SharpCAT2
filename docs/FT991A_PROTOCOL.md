# FT-991A CAT protocol fixture contract

This file freezes the Phase 1 protocol subset for independent fixture review. The fixtures are hand-written from the manufacturer manual; they are not generated by or shared with a production command builder, parser, or simulator.

## Source-backed operation table

Authority: Yaesu, *FT-991 CAT Operation Reference Book*, document filename `FT-991A_CAT_OM_ENG_1711-D.pdf` (revision suffix `1711-D`). The manual describes two-letter commands terminated by `;`, permits either command-letter case, and uses 9 decimal digits for FA/FB frequency values in Hz. The specified FA/FB set range is 30,000 through 470,000,000 Hz inclusive. It assigns ID 0670 to the FT-991A. MD parameter 1 selects receiver 0 (MAIN RX); parameter 2 is one character from the listed mode codes. SV is a set-only command with no reply. See page references in the table and fixtures.

| Operation | Request and response | Documented contract | Manual page (printed; PDF index) |
| --- | --- | --- | --- |
| Identity | `ID;` → `ID0670;` | Read-only identity query; `0670` identifies FT-991A. | 10; 10 |
| Frequency A | Query `FA;` → `FA` + 9 decimal Hz digits + `;`; set `FA` + 9 decimal digits + `;` | Set/query VFO-A frequency. Manual range 30,000–470,000,000 Hz inclusive. | 9; 9 |
| Frequency B | Query `FB;` → `FB` + 9 decimal Hz digits + `;`; set `FB` + 9 decimal digits + `;` | Set/query VFO-B frequency; same stated range as FA. | 9; 9 |
| Mode | Query `MD0;` → `MD0` + one mode code + `;`; set `MD0` + one mode code + `;` | `0` selects MAIN RX. Mode codes: `1` LSB, `2` USB, `3` CW-U, `4` FM, `5` AM, `6` RTTY-LSB, `7` CW-L, `8` DATA-LSB, `9` RTTY-USB, `A` DATA-FM, `B` FM-N, `C` DATA-USB, `D` AM-N, `E` C4FM. | 11; 11 |
| Swap VFOs | `SV;` | Set-only; manual lists no read or answer form. | 17; 17 |

The manual range is a device-command range, not a guarantee that every value is usable in every radio configuration. Nine digits establish wire syntax only. A syntactically valid number outside the documented range is rejected by this proposed API contract before transmission. Physical tuning restrictions and firmware-specific behavior are not inferred here.

## Proposed parser and operation outcomes

The fixture `expected.classification` distinguishes `valid`, `malformed`, `incomplete`, `invalidArgument`, and `identityMismatch`. A missing semicolon is `incomplete` because another byte could complete the frame. A semicolon-terminated command with wrong width, non-decimal frequency data, or invalid framing is `malformed`. A device reply with an unlisted MD mode code is malformed protocol data and yields `ProtocolError`. An API caller requesting an unlisted mode or a nine-digit frequency outside the manual's set range receives `InvalidArgument` before transmission. An otherwise well-formed ID answer other than `ID0670;` is `identityMismatch`.

Frequency and mode setters use write-then-read-back in the proposed client contract. Their fixture models no immediate reply with automatic information disabled; the follow-up query is a separate exact request/reply pair. The command table also marks FA, FB, and MD as supporting answers/automatic information, so an implementation must account for unsolicited reports if automatic information is enabled. SV has no reply, and verification is a subsequent pair of FA and FB reads. Do not treat a successful write as proof of state. Reading both frequencies can show the resulting pair changed when they differ; if both VFOs had the same frequency, the frequency pair alone cannot establish that a swap occurred. VFO selection is deferred; this subset does not define a select-VFO command.

`response: null` means the fixture expects no immediate CAT response. For an incomplete frame this means no dispatch/response is expected while the terminator is absent. These are protocol fixtures, not evidence of physical-radio behavior.
